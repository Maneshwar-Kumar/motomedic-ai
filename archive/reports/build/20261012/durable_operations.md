# Durable operation and saved-delivery build receipt

12 October 2026. Implementation candidate, synthetic local verification only.

TODO 7b and 9b now have a durable worker implementation. An accepted rider request atomically reserves visitor usage and a session turn, stores a hashed work snapshot and creates a named Cloud Task. A dedicated authenticated worker claims a Firestore lease before executing the existing private draft/verify pipeline. Browser SSE only observes stored progress and a saved accepted response. No serving daemon thread performs inference.

The operation state is QUEUED, RUNNING, COMPLETE or FAILED. Each operation has a 1,200-second deadline and fenced lease. Concurrent session turns fail before execution. Duplicate requests with the same payload recover the same operation; a changed payload cannot cancel it. An uncertain task-create acknowledgement preserves the outbox and retries the same hashed task name. Expired workers are terminally reconciled on redelivery, status read or the next session turn. They cannot repeat an uncertain provider call. A possibly successful final commit remains recoverable even if its acknowledgement was lost. Provider reservations remain the admission ledger's responsibility and are not cleared by operation reconciliation.

The worker binds provider admission to the operation's exact stored absolute deadline. Whole-turn admission consumes a slot before waiting, sleeps in at most 60-second intervals, then atomically rechecks its timing before returning a paid-call permit. Scheduler oversleep and slow transaction acknowledgement reposition the same consumed slot, preserving the existing rolling 10,000-token/minute limit. A one-second permit handoff allowance is included in the 61-second slot spacing. Deadline expiry, store failure or the fixed queue bound blocks transmission and retains reservations. Global admission identity hashes session ID plus the rider operation key; the rider key remains unchanged in the verifier and delivery proofs.

Exact coordinator-approved safety uses its separately identified source-scope method. Before clearing work, the commit transaction rechecks the immutable work hash and binds that proof's question/history hashes to the original stored inputs and its session hash to the updated session. It requires SAFETY_STOP and distinct source-scope/semantic flags. Private `accepted_source_scope_context` hashes are copied to the operation, session head and immutable session-version record; they contain no new raw question or history. Owned saved reads and duplicate recovery compare those independent hashes after work has been cleared. This storage binding does not grant source approval or create an eligible hazard.

Every current stream event has an operation ID and consecutive sequence. Answer chunks also carry the accepted response hash and exact Unicode offset. The complete event wraps the identical saved view. The client checks stream order, source/runtime/verification bindings and concatenated text. Neutral fixed fallback/error results emit no verified label or technical chunks. One-second durable polling and a 150-second observation timeout preserve the pending operation for recovery. A proven terminal failure clears the UI's pending request; uncertain failures preserve it.

Production startup now checks the v9 release policy, loads the generation/hash-bound index snapshot once, uses explicit inherited local query/reranker assets with downloads disabled, and loads the new serving retrieval/questions adapters. It no longer reads the held-out authored catalogue. An environment switch cannot enable Claude unless the exact release permits activation. Missing or partial durable-dispatch configuration fails closed; absent configuration cannot start provider work. The readiness result is false when verified serving lacks its required dispatcher.

## Hosting configuration still requires its existing authorization

The implementation reads `MOTOMEDIC_TASK_QUEUE`, `MOTOMEDIC_TASK_WORKER_URL` and `MOTOMEDIC_TASK_SERVICE_ACCOUNT`. The worker URL must be HTTPS with `/internal/operations/run`; the OIDC audience is that service origin. The worker verifies the token and the configured dedicated service-account email. Task bodies contain owner/operation/payload hashes; the rider question and history stay in the owner-private work snapshot. Cloud Tasks requires task-create and service-account act-as permission; the task identity requires private Cloud Run invocation. Queue retry duration must cover the operation deadline, and single concurrent dispatch is the candidate configuration. These are implementation requirements, not newly applied settings. The image command uses four request threads and a 1,200-second timeout so a worker request can progress while SSE observes it.

The API shape follows Google's primary [Cloud Tasks create reference](https://docs.cloud.google.com/tasks/docs/reference/rest/v2/projects.locations.queues.tasks/create) and [authenticated Cloud Run tasks guidance](https://docs.cloud.google.com/run/docs/triggering/using-tasks).
