## Startup boost and separate services

[Startup CPU boost](https://docs.cloud.google.com/run/docs/configuring/services/cpu) is already enabled. A 1-CPU limit receives 2 CPUs during startup and for 10 seconds afterward; boosted allocation is billed at the active CPU rate. With hypothetical five-second startup, boosted CPU costs 2 × 15 × $0.000024 = $0.00072 per start, plus $0.00001875 for 0.5 GiB memory over that interval. This is an illustration, not measured startup duration. Compare total billed CPU-seconds and wall time: faster startup can offset the higher rate. Avoid adding overlapping request seconds twice. Boost cannot remove network/download waits.

Qdrant's boot downloads and checksums stored immutable vector JSON and restores the collection. It never parses or embeds the manual per request. A future query API also needs BGE query-model assets, evidence registry and possibly the conditional reranker, plus a remote Gemma call; warming Qdrant does not warm that other process or the provider. The hosted benchmark's 56.64-second readiness excluding controls (38.25 seconds dense model/index load) is a GitHub worker measurement, not deployed Cloud Run cold-request latency. CPU/memory sizing and pricing for a future query service must follow memory/latency measurement; 512 MiB Qdrant sizing is not evidence that BGE fits there.

## Proposed bounded experiment, not executed

Before any setting change, define a fresh engineering allocation and deployment approval. On an isolated private revision with the identical immutable vectors/model revisions, measure at least ten verified cold starts and thirty warm requests for each tested setting. First instrument the current min0/boost-on baseline, recording revision and instance identity, startup/download/checksum/restore timing, query embedding, BM25/dense/reranker, source/eligibility gates, provider admission wait and TTFT, session commit, first safe SSE unit and complete client receipt. Confirm new instance identity rather than assume a sleep forces scale-to-zero.

Then compare boost on/off under min0, and optionally one minimum instance for a short scheduled demo window; each requires explicit setting-change authorization. Change one variable at a time, keep request mix/concurrency fixed, include failures and cold/warm distributions, and report billed CPU/memory seconds alongside latency. Ten cold samples are descriptive, not a strong p95 estimate. Include a fresh browser/public-network smoke test separately. Agree a small incremental cap (for example ₹20) and rollback time before execution; stop if the existing guard stops billing, without re-enabling it.

For the future query service, compare pinned model assets packaged in the image against startup downloads; record image pull cost/time as well. Load models once per worker, reuse them across requests, perform bounded readiness warmups, and keep immutable ingestion/index reuse. These are candidate improvements requiring matched tests. The present recommendation is min0 and current boost-on, with optional brief min1 only if measured cold delay makes a named demo unusable and a separate budget allocation covers it.
