03 Technical requirements
TRD v0.4  Reference design and implementation contracts
DRAFT v0.4  Updated 9 October 2026  Independent source review pending
TRD v0.4 is the authoritative design and technical contract as of 9 October 2026. This document follows it. The approved owner manual governs motorcycle facts; source applicability, rights, independent review and release gates remain mandatory. Recorded implementation progress does not constitute release approval.
1  Design philosophy and trust boundaries
This specification describes a version-locked, layout-aware multimodal RAG pipeline using only the supplied Royal Enfield New Himalayan 450 owner's manual with diagnostic session state. The LLM may translate a customer report into structured observations and paraphrase manual-backed instructions. No model may author a new repair step absent an applicable evidence object.

2  Versioned hosted ingestion pipeline
Register manual: OEM, model, year range, variant, document edition, original URL, local hash SHA-256, language and rights status
Parse each page with Docling or another layout-aware parser; retain PDF index, printed page label, headings, reading order, tables, images, warning/caution objects and bbox
Create typed evidence objects: PROCEDURE, STEP, CONDITION, WARNING, SPEC_TABLE, TABLE_ROW, FIGURE, SECTION, CROSS_REFERENCE
Apply hierarchical or hybrid chunking to the typed structure; enrich each child with section path and variant; preserve full parent procedure for answer assembly
For tables, repeat headers, dimensions/units and variant tags; never embed anonymous numeric cells without headers
For images, store page crop, caption, nearby explanatory paragraphs and figure relationship; uncertain diagram interpretation is a review flag
Build a dense vector index and sparse BM25 index; link both to stable evidence IDs; do not regenerate on every request
Build explicit edges from headings, figure links, in-document cross-references, preconditions, warnings and NEXT_STEP references
Run ingestion QA: page/object counts, missing pages, table header preservation, warning detection and extraction confidence flags

4  Retrieval + evidence assembly contract
First-stage dense retrieval uses cosine similarity or the embedding model's recommended metric. Sparse BM25 retrieval handles exact warning labels, component codes and units. Fuse ranks with Reciprocal Rank Fusion, assemble initial parent and verified dependency context, and inspect ranking uncertainty separately from source applicability and evidence coverage. Conditionally rerank a bounded candidate pool before reassembly and the controller/answer gates.
The hosted prototype uses a fused pool of 20 candidates and selects five hits for assembly. One recovery may widen the fused pool to 40 and fetch exact reviewed dependency IDs. Reranking scores at most 20 candidates and 100 token-bounded query/passage pairs. At most 256 mandatory dependency IDs may be attached; an over-limit manifest fails as SYSTEM_ERROR and must not be silently truncated. These limits and trigger thresholds are versioned starting hypotheses, to be calibrated on independently reviewed cases.
Apply hard filters by selected manual ID, model/variant, publication version and language before ranking
Edge expansion should be selective: always include required warnings/prerequisites; retrieve only referenced figures/specifications, not the whole manual
For each candidate, compute evidence coverage over requested step, conditions, warnings, variant-specific values and referenced sections
If an approved dependency set is incomplete, permit one bounded recovery that fetches the exact required objects and widens retrieval once. If dependencies remain unavailable, withhold technical advice and record a non-rider-resolvable source gap. Allow at most one subsequent reranking attempt when ordering remains uncertain and all source/applicability checks permit it; never loop between search, reranking and generation.
Cosine similarity and reranker scores are relevance heuristics, never proof that an instruction is supported
4 1 Evidence dependency manifest
During versioned ingestion, bind each searchable child chunk to its full parent procedure or section and build a reviewed dependency manifest for every actionable step. The manifest identifies the action spans, applicability conditions, prerequisites, warnings, table headers and units, variant labels, and referenced figures or sections required to present that step. A section parent remains contextual evidence until its procedure and step boundaries have been reviewed.
The assembler returns required_evidence_ids, attached_evidence_ids and missing_evidence_ids for the selected candidate, together with dependency_manifest_version and dependency_review_status. missing_evidence_ids is the required set minus the attached set. Coverage is complete only when the dependency manifest is approved for the exact manual checksum, the action evidence is present, all required objects are attached, and their content and provenance pass extraction checks. An empty or unreviewed required set cannot establish sufficiency. Finding a table object is insufficient if its required headers, units or variant context are missing.
Perform the existing bounded recovery search for missing dependencies and record its outcome. A source gap that the rider cannot resolve must block the instruction and enter source review or abstention; do not ask the rider to supply a missing manual warning or table header. Retrieval outages, invalid index objects and other operational failures return SYSTEM_ERROR. Cross-encoder scores rank relevance and cannot approve a dependency manifest, infer a diagnostic order or waive missing evidence.
4 2 Conditional reranking and bounded recovery
The normal request path uses conditional reranking. Clearly ordered candidates with complete reviewed dependencies continue to the eligibility and answer gates. Reranking handles uncertain ordering among plausible candidates; evidence recovery handles required objects absent from the initial bundle. Similarity, RRF and cross-encoder scores cannot prove support or approve a procedure.
Trigger signals compare distinct parent sections: disagreement between dense and BM25 top sections, or a narrow relative RRF margin between the two leading sections. Sibling chunks from the same section do not create ambiguity. Zero BM25 matches provide no sparse-agreement signal. Initial experimental values are top-three section overlap below 0.5 or relative RRF margin at most 0.05. Mark these values PROVISIONAL_UNCALIBRATED; use reviewed tuning cases to calibrate them and held-out cases to assess their effect before a release decision.
Apply the routing policy in order. A known safety stop retains its verified warning and skips model work; a known system failure remains SYSTEM_ERROR; a known unsupported request abstains. Missing, stale or unapproved source/dependency review enters source review or abstention. Unconfirmed applicability enters one focused clarification; a confirmed mismatch blocks the action. An approved missing dependency triggers one exact-ID fetch and bounded retrieval expansion. Complete eligible evidence with uncertain ordering triggers one cross-encoder attempt; otherwise continue through the remaining gates.
Reassemble after reranking and recheck the dependency set. Retain all already fetched mandatory action, warning, prerequisite, table/header/unit and figure objects for the selected reviewed step even when candidate ordering changes. Reranking does not select a new diagnostic step or infer an OEM order. The controller remains responsible for selecting an eligible step and the final verifier remains responsible for claim support.
Operational failures in embedding, retrieval, assembly or the cross-encoder yield SYSTEM_ERROR with a typed error class and recorded attempts. A query exceeding the current cross-encoder's 128-token input bound, or work exceeding 100 query/passage pairs, skips that inference with an explicit reason and keeps ranking unresolved. Preserve the full query and source text; never silently truncate a rider report or mandatory evidence. A source gap cannot be resolved by asking the rider to supply a missing manual warning or table header.
Return a RetrievalDecision with policy version/configuration, calibration status, execution mode, uncertainty signals, decision history, recovery/rerank attempt counts, exact missing/fetched evidence IDs, pair count, skip reason and stage durations. Conditional mode is the normal code path; off and always_diagnostic modes exist only for ablations. Always-diagnostic execution can bypass the scheduling decision but cannot bypass evidence, applicability, safety or answer-release gates. A generic insufficient-bundle flag must never trigger reranking by itself.
The current hosted manual has pending applicability and independent dependency review. Its candidate bundles therefore skip conditional reranking with explicit review/clarification reasons and keep may_generate_procedural_advice false. The implementation is available for approved registry/controller inputs; source and release approvals are separate work. Changing this policy versions retrieval and invalidates affected response caches while reusing unchanged document embeddings.
Evaluate off, always and conditional policies on the same independently reviewed cases. Record complete evidence recall, rescued and regressed cases, proper abstention, wrong-variant leakage, trigger precision/recall, reranking frequency, per-stage latency, TTFO and cost per correctly handled case. Adopt calibrated conditional reranking for release only if it improves reviewed outcomes without violating latency/cost and safety gates. The existing 27 draft in-sample page-coverage probes cannot establish that result.
Cross-encoder retrieval reference: https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html
5  Diagnostic state machine and adaptive branching
A deterministic controller stores the diagnostic session separately from the LLM chat transcript. The controller accepts typed feedback and selects eligible actions only from the verified procedure graph. Generation occurs after next-step selection, never before.
5 1 Reviewed step registry and rule authoring
Create candidate StepDefinition and ApplicabilityRule records from the original owner manual during ingestion. A layout parser or model may propose the records, but an independent reviewer must check each action, condition, prerequisite, warning and stopping condition against the original pages before it becomes runtime-authorized. Record the reviewer, decision, source spans and registry version. Draft, rejected, stale or checksum-mismatched rules must not authorize an action or a cached answer.
Every manual-derived predicate must retain its supporting evidence IDs and page provenance. Record origin as MANUAL for OEM conditions and PRODUCT_POLICY for application behavior such as avoiding repeated attempts; policy rules carry their own version and must never be presented as OEM instructions. Relevance tags and rider intent mappings help select candidates, while the reviewed predicates establish applicability. Uncertain interpretation of the rider report remains an unknown observation until clarified.
When the manual lists possible causes or independently documented checks without branch conditions or an explicit next-step order, preserve those limits. Do not infer a condition, eliminate an undocumented branch, diagnose a fault from a negative clue or claim an OEM ranking from retrieval scores. The existing SM-04 policy governs selecting among independently documented eligible checks.
5 2 Three valued eligibility checks
Evaluate reviewed conditions against typed session facts using TRUE, FALSE and UNKNOWN. A condition is UNKNOWN when its observation is missing, uncertain or invalid; a confirmed mismatch is FALSE. A step is ineligible when any required condition is FALSE, its source or review status is invalid, its branch has been validly excluded, or its attempt history blocks repetition. If no required condition is false but a relevant condition is unknown, withhold the action and ask one reviewed source-derived question when the rider can reliably resolve it. Unknown is never treated as true or normal.
An action becomes eligible only when the manual and variant match, the rule is approved, the symptom or documented branch applies, required conditions and prerequisites are true, no applicable safety rule prohibits it, and the attempt history allows it. Evaluate the evidence-completeness and answer-release gates separately before issuing technical text. A direct factual lookup uses the same applicability and evidence gates without fabricating a diagnostic step.
Implement rule predicates with allowlisted typed comparisons such as enum equality, boolean facts and numeric comparisons with explicit units. Treat the PDF and model output as data; do not execute extracted expressions as code. Return an EligibilityDecision with each condition result, reason code, evidence reference, registry version and session version. ACTION_COMPLETED_UNRESOLVED records an attempted action and never supplies an OBSERVED_NORMAL fact. Optional interpretation models may propose typed observations or rank already eligible candidates; their output cannot bypass the controller gates.

6  Evidence sufficiency and output validation
Apply two layers: a deterministic rules gate (valid manual, cited evidence IDs, required dependencies, prerequisites/variant, no explicit conflict) plus a semantic support evaluator that compares each proposed technical claim against relevant source spans. Reject the draft if either layer fails.
6 1 Response routing and release
The controller selects the response route from structured eligibility decisions, the evidence bundle and gate results. A known applicable stop condition yields SAFETY_STOP and retains its verified warning even if other processing fails. Otherwise, a required component failure yields SYSTEM_ERROR. A resolvable missing applicability fact or documented branch observation yields AMBIGUOUS and one focused question. After bounded recovery, an unsupported request, an unresolved source gap or exhausted documented paths yields UNSUPPORTED with the verified support route.
SUPPORTED requires an eligible action or applicable factual answer, an approved and complete dependency set, valid citations, satisfied safety and prerequisite checks, and successful final claim validation. The controller may authorize generation of a draft after next-step selection; the final response is marked SUPPORTED only after both validation layers pass. Rejected drafts remain withheld. Retry within a bounded policy, then return SYSTEM_ERROR for generation/verification failure or UNSUPPORTED for an established source gap; never disguise a system failure as absence in the manual.
Gate result
Behavior
SUPPORTED
Release a concise answer or eligible documented action only after applicability, dependency completeness, warnings, citations and final claim-to-source validation pass.
AMBIGUOUS
Ask one focused source-derived question about an unknown branch observation or resolvable applicability fact; withhold the dependent action.
UNSUPPORTED

Even a high-scoring semantic verifier can make mistakes; guarantee only that the application follows the fail-closed protocol, not that all semantic classifications are infallible. Output citations must map to immutable evidence object IDs, not model-created page numbers.
7  Multimodal path
Photo input: validate size/type, run vision extraction into observations {component_hint, visible_feature, uncertainty, needs_clarification}; no root-cause diagnosis from vision alone
Document diagrams: associate image with figure, heading, parent procedure and original page crop; require model verification against the image for image-dependent claims
Voice input P1: use speech-to-text (Sarvam or alternative), show/edit transcript, and route to identical RAG evidence checks; speech duration, STT latency and STT spend are separately reported
No permanent public-demo storage of image/audio by default; avoid putting raw media or personal text into traces

11  Deployment, security and reliability
Host a Streamlit UI at a shareable URL; keep API keys server-side in secrets management; pin dependencies and models
Package a small prebuilt index snapshot and verified document graph or use managed Qdrant if local resource limits are unacceptable
Apply file size/type limits, per-user rate limits and a per-day spending cap; sanitize PDF text as data, not executable instructions
Do not include proprietary manuals in an unrestricted public repository without verifying usage rights; use private asset storage or a permitted manual
Graceful errors use SUPPORTED, AMBIGUOUS, UNSUPPORTED, SAFETY_STOP and SYSTEM_ERROR under section 6 1. Review gaps block advice; rider-resolvable applicability facts clarify; confirmed mismatches block; operational failures remain SYSTEM_ERROR.
12  Evaluation, ablations and versioning
Evaluate at least 25 gold records for an MVP; expand to 50–100 with the supplied manual. Include multi-turn transcripts and photo inputs, required evidence sets, forbidden claims and outcome expectations. Always annotate independently from the tested model where feasible.
12 1 Eligibility and assembly regression cases
Include independently reviewed cases that verify rule provenance and expected eligibility decisions, in addition to retrieval relevance and answer wording. Record expected condition results, exclusion reasons, required evidence IDs, response route and allowed next step for each case.
TRUE, FALSE and UNKNOWN facts select, exclude or clarify the documented branch correctly; unknown facts and unresolved attempts never become normal observations.
Draft, stale, wrong-variant and checksum-mismatched step rules cannot authorize technical text or cache hits; every manual-derived predicate resolves to its reviewed source spans.
A relevant child chunk with a missing prerequisite, warning, table header/unit or referenced figure cannot pass the completeness gate. A missing or unapproved dependency manifest also fails closed.
Distinguish a resolvable observation from a source gap, a known safety stop and an operational failure. Exhausted paths escalate; relevance scores cannot invent a step or repeat a completed action without the documented exception.
Keep the existing release targets. Report unsupported eligibility approvals and unjustified repeat steps alongside next-step correctness, complete evidence recall, answerable coverage and proper abstention; adjudicate failures against the original manual and reviewed policy rules.

13  Unresolved engineering risks
Visual table or diagram extraction could silently lose prerequisites, units or warnings
Manual may not contain a true decision tree or enough alternatives for adaptive troubleshooting; OEM referral remains valid end state
Closed-model semantic validators may exhibit false acceptances and false refusals; measure both
Hosted free-tier cold starts and egress constraints can dominate model-side latency
Model identity hallucination from photos can cause incorrect manual routing; require confirmed bike variant
